## Эксперимент 1. Кого оставили в лотерее (15–20 минут)

```bash
uv run python $P/01_sampling.py
open $P/out/01_sampling.png
```

Условные кандидаты имеют исходные вероятности:

```text
Париж — 0.60
Лион — 0.25
город — 0.10
бегемот — 0.05
```

Это выдуманный пример, а не ответ реальной модели о столице Франции. Нельзя считать эти числа оценкой фактической уверенности Gemini.

Четыре режима:

1. `T=1`, `top_p=1`: исходное распределение.
2. `T=0.5`, `top_p=1`: первый кандидат получает примерно `0.828`.
3. `T=1`, `top_p=0.8`: остаются первые два кандидата с вероятностями примерно `0.706` и `0.294`.
4. `T=0`: наш явный жадный выбор; первый кандидат выигрывает все попытки.

Тысяча попыток — это тысяча независимых выборов **для одного фиксированного контекста**. Настоящая генерация предложения после каждого токена пересчитывает предсказание.

Посчитай новые доли после перенормировки. Почему нельзя выбросить второй токен на том основании, что он «перешёл порог»?

### Задание 1.2. Порог совпал ровно

Добавь в `scenarios` вариант с `T=1` и `top_p=0.6`. Должен ли остаться второй кандидат?

В коде есть маленькая поправка на округление float: вычисленное `0.5999999999999999` в этой лаборатории считается достижением порога `0.6` с допуском в один соседний float. Это численная деталь реализации, а не изменение идеи top-p.

### Задание 1.3. Температура и фильтр — разные действия

Добавь вариант с `T=0.5` и `top_p=0.8`. Сначала температура усиливает лидера, потом применяется фильтр. Сколько кандидатов осталось теперь?

Почему одинаковое значение top-p при разных распределениях может оставлять разное число токенов?

## Эксперимент 2. Не пересчитываем старые K и V (20–25 минут)

```bash
uv run python $P/02_kv_cache.py
open $P/out/02_kv_cache.png
```

Есть 12 заранее заданных входных векторов. Первые четыре — условный начальный префикс, остальные добавляются по одному.

Для каждого текущего префикса сравниваются:

- полный пересчёт его K и V и результата последней позиции;
- использование сохранённых K и V плюс проекции одной новой позиции.

Здесь одна голова, нет настоящих токенов, RoPE, MLP и всей многослойной модели. Новый входной вектор уже известен программе — текст она не генерирует.

### Что получилось на исходных данных

- Выходы совпали в пределах `1e-12`; наблюдавшиеся различия — порядка `1e-16`.
- При длинах от 4 до 12 полный повторный расчёт затронул `4 + 5 + … + 12 = 72` позиции для K/V.
- Кэшированный вариант обработал первые четыре один раз и ещё восемь новых: всего `12` позиций.

Каждый счётчик описывает свой способ по отдельности. Проверочная программа реально выполняет **обе ветки**, поэтому это не счётчик всех операций самого скрипта.

**72 против 12 — не измеренное ускорение в секундах.** Реальный сервер тратит время на остальные слои, память, запуск вычислений и другие операции.

### Задание 2.1. Где прошлое, а где новое

Найди `prefill()` и `decode_step()`.

- Что хранится в кортеже `cache`?
- Какие матрицы считаются заново для одной добавленной позиции?
- Почему в этой функции все переданные ключи уже относятся к разрешённому прошлому или текущей позиции?

Подумай: если слепо использовать треугольную маску из одной строки с номером ноль, не спрячем ли мы большую часть настоящего прошлого?

### Задание 2.2. Почему старый кэш стал неправильным

Скрипт изменяет первый входной вектор, но пробует использовать сохранённый старый кэш. Проверка совпадения даёт `False`.

Почему это ожидаемо? Должно ли приложение разрешать такой кэш только потому, что отредактированный текст «о том же самом»?

Наша игрушка не хранит хеш префикса, версию модели или позиции. Она показывает числовую ошибку неправильного переиспользования; контроль совместимости в настоящей системе — отдельная обязанность.

### Задание 2.3. Память не исчезла

В оценке условной многослойной модели:

```text
2 массива (K и V)
× 32 слоя
× 8 KV-голов
× 128 чисел на голову
× 8192 сохранённых токена
× 2 байта
= 1 073 741 824 байта = 1 ГиБ
```

При тех же параметрах посчитай память для 16 384 токенов и для двух одновременных последовательностей по 8192 токена.

Почему этот расчёт не равен всей памяти модели? Почему нельзя автоматически взять число байтов на элемент кэша из квантизации файла весов?

Это отдельная условная конфигурация, **не размеры массивов маленькой головы** из первого графика. Она предполагает одинаковую размерность K и V.

### Задание 2.4. Скорость и корректность — разные проверки

Нашли вариант, где результатов меньше пересчитывается. Какие дополнительные измерения потребуются, чтобы честно сказать «мой сервис стал быстрее»?

Назови минимум три условия: например, одинаковая длина ответа, прогретость, размер входа, аппаратная конфигурация, нагрузка и память.

## Автоматические проверки

```bash
uv run python -m unittest discover -s "$P" -v
```

Ожидается **17 тестов, OK**. Они проверяют:

- температуру, жадный выбор и корректную границу top-p;
- сохранение положительного хвоста при `top_p=1`;
- нормировку и устойчивость распределения;
- совпадение кэшированных шагов с пересчётом префикса;
- рост кэша на одну позицию без изменения старых массивов;
- ошибочность устаревшего кэша после изменения входа;
- арифметику памяти и её масштабирование по токенам и батчу.

Это проверки учебной математики. Они не доказывают качество ответов, скорость или стоимость настоящего API.
