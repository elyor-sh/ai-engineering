## Часть 2. Локальный селектор (15–20 минут)

```bash
uv run python $P/01_model_selection.py
```

**Имена `demo-*` не являются настоящими API ID.** Значения качества, задержки, стоимости и возможностей выдуманы. Они ничего не говорят о качестве или ценах Gemini, Claude, GPT или локального Qwen.

В учебной таблице предполагается, что:

- качество оценено по одному общему критерию на одном наборе;
- месячная стоимость относится к одной и той же нагрузке и согласованным затратам;
- у профилей известны отдельные лимиты входа/выхода и общий предел;
- оценки токеновых бюджетов сопоставимы в рамках этой игрушки.

В реальности текст нужно оценивать для каждого токенизатора, лимиты — читать у конкретного API, а полную стоимость и качество — отдельно проверять.

### Демонстрационные профили

| Профиль | Размещение | Качество | p95 | Месячная цена |
|---|---|---|---|---|
| `demo-local` | local | 0.86 | 6 с | $50 |
| `demo-cloud-fast` | cloud | 0.91 | 2 с | $540 |
| `demo-cloud-large` | cloud | 0.96 | 8 с | $2500 |
| `demo-cloud-alternate` | cloud | 0.89 | 3 с | $700 |

Остальные учебные лимиты и флаги находятся в `demo_candidates()`.

### Сценарий 1. Жёсткие условия

Требуется:

- качество не ниже `0.90`;
- p95 не выше `5` секунд;
- месячная стоимость не выше `$1000`;
- вход `10 000` токенов, резерв выхода `1000`;
- поддержка обязательного структурированного вывода;
- облако разрешено.

Ожидаемый короткий список: **только `demo-cloud-fast`**.

**Задание 2.1.** Объясни, почему `demo-cloud-large` с наивысшим качеством не проходит. Почему бесплатность не должна компенсировать недостаточное качество, если минимум действительно обязателен?

### Сценарий 2. Облако запрещено

Все условия прежние, но передавать данные в облако нельзя.

Ожидаемый результат: **пустой список**.

**Задание 2.2.** Почему это корректно? Предложи два следующих шага, не нарушающих запрет. Считается ли автоматический облачный fallback подходящим решением?

Уточнение: это учебная проверка по полю `hosting`, а не аудит сетевых соединений. Настоящий маршрут и права проверяются отдельно.

### Сценарий 3. Другая задача и компромиссы

Для отдельного учебного сценария порог качества снижен до `0.85`, задержка разрешена до `10` секунд, бюджет — `$3000`, вход — `6000`, а структурированный вывод не обязателен.

Это **явно другая постановка**, а не разрешение тихо ослабить условия первого сценария.

Все четыре профиля допустимы. По качеству, цене и задержке граница Парето содержит:

```text
demo-local
demo-cloud-fast
demo-cloud-large
```

**Задание 2.3.** Почему `demo-cloud-alternate` доминируется быстрым вариантом? Почему локальный дешёвый и большой качественный профиль всё ещё остаются, хотя не выигрывают по всем показателям?

**Задание 2.4.** Назови две важные характеристики, которых нет в этой тройке сравнения. Как они могли бы изменить окончательное решение?

### Задание 2.5. Отдельный лимит не равен общему

В `Requirements` есть резерв выхода. В `rejection_reasons()` проверяются и отдельные пределы, и сумма входа с резервом против общего контекста.

Почему проверять только `input_limit` и `output_limit` недостаточно для профиля с общим пределом? Вспомни бюджет из урока 1.3.

## Автоматические проверки

```bash
uv run python -m unittest discover -s "$P" -v
```

Ожидается **13 тестов, OK**. Проверяются запрет облака, обязательные функции, качество, цена, задержка, отдельные и общий лимиты, пустой результат и строгое доминирование.

Если меняешь сам учебный каталог, тесты с ожиданиями исходных имён и списков могут измениться. Сначала пойми новый результат; не переписывай проверку только ради зелёной галочки.

**Границы реализации:** программа не читает реальные лицензии, не проверяет утечки, не измеряет модели, не учитывает неопределённость оценок и не подтверждает достоверность исходных метрик. Отсутствие NaN — не доказательство качества данных. Это упражнение по логике решения, не готовый production-роутер.
