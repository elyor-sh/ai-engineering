## 🧾 Три способа получить «JSON» — с разными обещаниями

### Способ первый: попросить в тексте

Можно написать в инструкции: «Верни только JSON с такими полями». Это полезная подсказка модели, но сама по себе она не является техническим ограничением формата.

Модель может добавить пояснение, Markdown-ограждение, лишний ключ или недопустимое значение. Даже при хорошем промпте результат нужно разбирать и проверять.

Такой подход иногда достаточен для прототипа, но не нужно приписывать ему гарантию схемы.

### Способ второй: JSON mode

Некоторые API поддерживают специальный режим, нацеленный на синтаксически корректный JSON. В совместимом интерфейсе он может обозначаться как `json_object`.

Это не обязательно обещание конкретных полей и типов. Объект может быть валидным JSON, но содержать другие ключи или строку вместо ожидаемого числа.

Некоторые сервисы требуют дополнительно явно упомянуть JSON в инструкции. Ограничение длины, отказ и ошибки всё равно обрабатываются отдельно. Нельзя обещать один и тот же режим всем моделям.

### Способ третий: структурированный вывод по схеме

При **Structured Outputs** приложению доступен механизм передачи схемы желаемого результата. В поддерживаемой реализации она может участвовать в ограничении допустимой генерации, например через constrained decoding.

Сервис обещает определённое соответствие поддерживаемому контракту, а не просто хорошее намерение модели. Но нужно читать условия: какие схемы допустимы, какие модели и endpoint работают, что происходит при отказе или усечении.

Это сильнее текстовой просьбы, но не проверка истины. Правильный целочисленный ID всё ещё может обозначать другую заявку.

## 🧩 Из чего состоит JSON Schema

**JSON Schema** — способ описать допустимую структуру данных. Это не инструкция в свободной прозе и не сама заполненная заявка.

В простом контракте понадобятся несколько элементов.

**Type** задаёт вид значения: объект, строка, целое число, массив, логическое значение или null.

**Properties** описывает поля объекта и их схемы.

**Required** определяет, какие ключи обязаны присутствовать. Наличие поля в properties само по себе не всегда делает его обязательным.

**Enum** ограничивает значение набором вариантов. Например, категория должна быть одной из заранее известных меток.

**Additional properties** определяет отношение к неизвестным ключам. Если лишние поля запрещены, модель не должна добавлять произвольное `is_admin` или ещё один непредусмотренный параметр.

**Description** помогает объяснить назначение поля. Но описание «только подтверждённый email» не превращается автоматически в проверку реального владельца адреса.

В JSON Schema есть и другие возможности: вложенные объекты, массивы, ограничения чисел, строк и сочетания схем. Поддержка полного стандарта в конкретном генеративном API не гарантируется.

## ❓ Обязательное, неизвестное и отсутствующее — разные состояния

Допустим, источник содержит номер заявки и проблему входа, но контактного email нет.

Есть как минимум три разные структуры контракта:

- ключ email обязан быть и содержать строку;
- ключ email обязан быть, но может содержать строку или null;
- ключ email можно не передавать вообще.

Это разные решения. Если заставить модель выдать строку там, где данных нет, мы создаём давление угадывать.

Для нашей лаборатории ключ `contact_email` будет **обязательным, но допускающим null**. Null означает отсутствие значения в рамках задачи, а не пустую строку, не текст «неизвестно» и не выдуманный адрес.

В Python ему соответствует None. В самом JSON нужно слово `null`, а не Python-запись `None`.

### Категория other и категория unknown тоже различаются

`other` может означать: данных достаточно, но ни одна специализированная категория не подходит. `unknown` — классификация пока недостаточно обоснована.

Конкретную таксономию определяет приложение. Важно не складывать разные причины неопределённости в одну непрозрачную метку.

Если обязательного ID нет в источнике, решение не в том, чтобы заставить модель угадать. Нужно изменить контракт или обработать невозможность извлечения: уточнение, отказ, отдельный статус или nullable-поле, если это соответствует задаче.

## 🐍 Pydantic: контракт рядом с Python-кодом

Pydantic помогает описать модель данных типами Python, проверить вход и получить объект с ожидаемой структурой. В этом уроке используем **Pydantic 2**.

Для примера опишем черновик заявки:

- `request_id` — целое число;
- `category` — одна из меток access, billing, other или unknown;
- `contact_email` — строка или None, но сам ключ обязателен.

Из такой модели можно получить JSON Schema через `model_json_schema()`. После разбора JSON можно проверить словарь через `model_validate()`. Есть и удобный путь `model_validate_json()`, совмещающий разбор текстового JSON с проверкой модели.

Для выдачи данных обратно существуют `model_dump()` и `model_dump_json()`. Не нужно путать описание схемы, экземпляр данных и его строковое представление.

### Почему настройки важны

Некоторые валидаторы допускают преобразования типов. Это может быть удобно: строка с цифрами превращается в число. Но для строгого извлечения хочется увидеть нарушение, а не незаметно скрыть его.

В нашей модели зададим строгую проверку типов и запретим дополнительные поля. Строковый ID «28» не будет принят как целочисленный 28; лишний ключ не исчезнет молча.

В Pydantic 2 аннотация «строка или None» без значения по умолчанию может оставаться обязательной. Если явно задать default None, это уже меняет обязательность. Посмотрим на required в полученной схеме, а не будем судить только по внешнему виду аннотации.

## 🔒 Два разных strict

Здесь легко запутаться.

**Строгая локальная валидация** управляет тем, какие значения принимает наш Python-код и какие преобразования допускает.

**Строгий режим схемы у провайдера**, если он поддерживается, относится к его контракту структурированного вывода.

Наличие первого не включает автоматически второй. Если описать класс Pydantic, но не передать нужные инструкции и схему в API, сервер не узнает о нём магическим образом.

И наоборот: запрос схемы у сервера не отменяет локальную проверку. Могли измениться версия модели, схема, адаптер или тип результата. Для действий с последствиями нельзя строить всё на предположении «провайдер обещал».

SDK может предоставлять удобный метод автоматического parse с моделью данных. Это облегчает работу, но не гарантирует поддержки такого метода любым совместимым сервером и не проверяет все бизнес-условия.

## 🪜 Четыре уровня проверки

Построим лестницу приёмки.

### Первый: подходящий завершённый результат

Убедиться, что это именно ожидаемый текстовый ответ, а не отказ, запрос инструмента, обрезка `length`, пустое поле или оборванный поток.

Structured Outputs не отменяет разные исходы API. Отказ может обрабатываться вне схемы, а ограниченный результат не стоит насильно превращать в законченную структуру.

### Второй: JSON разбирается

Ответ должен быть целым JSON, а не пояснением с JSON где-то внутри. Markdown-ограждения тоже являются посторонним текстом для строгого парсера.

В лаборатории отдельно отклоняем повторяющиеся ключи. Некоторые разборщики могли бы оставить последнее значение, но для нашей приёмки такой ответ неоднозначен. JSON Schema, применённая уже после потери дубликата при разборе, не обязана обнаружить его.

Не используем eval: ответ модели — данные, а не Python-код для исполнения.

### Третий: типы и структура подходят

Проверяем нужные ключи, их типы, допустимые метки и отсутствие лишних полей. Здесь работает наша модель Pydantic.

### Четвёртый: данные и действие обоснованы

ID должен совпасть с источником, контакт не должен быть выдуман, классификация — соответствовать задаче. Дальше отдельно проверяются права и допустимость действий.

Например, ID 82 является правильным целым числом, но не номером 28 из исходного сообщения. Схема это противоречие сама не вычислит, если её задача — разрешать целые ID вообще.

---

## 🔎 Что можно проверить обычным кодом

Если у нас есть независимо известный ID или значение из авторитетной системы, их можно сравнить с результатом. Если контакт явно отсутствует, можно отклонить придуманную строку.

Но важно понимать происхождение этих «известных» фактов. Если их тоже без проверки придумала та же модель, независимость исчезает.

В нашей лаборатории правильный ID и отсутствие email заданы в учебной разметке источника. Это позволяет проверить **два конкретных факта**, а не построить универсальный детектор галлюцинаций.

Категория может быть допустимой по enum, но неверной по смыслу. Если в программе нет соответствующего независимого критерия, нельзя объявлять классификацию проверенной только потому, что остальные поля совпали.

Так мы продолжаем урок 1.8: синтаксис, структура, соответствие данным и полномочия не подменяют друг друга.

## 🔌 Передача схемы не универсальна для всех API

В совместимом Chat Completions структурированный формат может задаваться через `response_format` с JSON Schema. У других интерфейсов поля и способы настройки отличаются.

В частности, собственные API Gemini, Anthropic и OpenAI могут предоставлять разные механизмы. Даже совместимый endpoint может поддерживать лишь часть возможностей.

Проверяют:

- конкретную модель и endpoint;
- допустимую форму схемы;
- required, nullable и дополнительные свойства;
- поддержку ссылок, вложений и ограничений;
- поведение при отказе, ограничении длины и ошибке;
- ограничения размера и сложности схемы.

Схема, сгенерированная библиотекой, может содержать элементы, которые сервер не принимает. Пользовательский Python-валидатор тоже не обязан автоматически превращаться в удалённое ограничение генерации.

Поэтому «одна модель данных для всего» — хорошая цель для уменьшения расхождений, но не повод не проверять адаптер.

### Не скрываем понижение гарантий

Если сервер отверг JSON Schema, нельзя без уведомления отправить запрос ещё раз только с текстовой просьбой и продолжить говорить о тех же гарантиях.

Можно заранее выбрать другой поддерживаемый режим и оставить строгую локальную приёмку. Но это другое осознанное решение, а не незаметный fallback. Каждая новая попытка может расходовать квоту и деньги.

## 🌊 Что меняется при стриминге

В уроке 2.3 мы собирали текст по частям. Начало объекта ещё не является полным JSON: строка или массив могут быть не закрыты, поля — не получены.

Можно показывать предварительное состояние интерфейса или использовать библиотеку с подходящими событиями структурированных данных. Но выполнение действий должно ждать нужного завершённого и проверенного результата.

В текущей практике используем полный нестриминговый ответ, чтобы ясно увидеть уровни проверки. Это не отменяет предыдущий урок: перенос на поток требует корректно совместить оба контракта.

Нельзя считать, что ранняя успешная проверка кусочка доказывает корректность ещё не пришедших частей.

---

## 🛠 Ошибка валидации — сигнал, а не приказ угадать

Получили неправильный тип или отсутствующее поле. Что дальше?

Возможные решения: сообщить об ошибке, запросить уточнение, выполнить ограниченную повторную попытку, передать человеку или исправить сам контракт и данные.

Зависит от причины. Если обязательный факт отсутствует в источнике, новая просьба «заполни все поля любой ценой» только поощряет выдумку. Если режим не поддерживается, смена температуры не добавит поддержку API.

Автоматическое исправление бывает полезно, но его нужно ограничивать, учитывать стоимость и повторно валидировать результат. Нельзя бесконечно перезапрашивать модель, пока один ответ случайно не пройдёт тест.

Ремонт формата и изменение фактов тоже различаются. Молча поменять неправильный ID на «более удобный» — не то же самое, что согласованно обработать техническое оформление.

Полную политику надёжности разберём в уроке 2.7. В этой лаборатории нет автоматических повторов и скрытой смены режима.

## 🧬 Версии схемы и безопасная диагностика

Добавление обязательного поля может сломать прежние сохранённые ответы и клиентов. Запрет лишних ключей делает неожиданное расширение заметным, но требует осмысленного обновления контракта.

Поэтому полезно фиксировать версию схемы или приложения, тестовые примеры и ожидания. Не нужно удалять неудобную проверку только ради зелёного результата.

Сообщения валидатора могут включать исходные значения. Если там email, персональные данные или внутренние тексты, полный вывод ошибки может стать утечкой.

В практике показываем путь поля и тип нарушения, а не автоматически печатаем весь вход из ValidationError. И не отправляем секреты в промпт «почини JSON».

Структурированный результат остаётся недоверенными входными данными для следующей системы. Строка с аргументом не должна самопроизвольно становиться shell-командой или авторизованным действием.

## ⚠️ Частые ошибки

**«Попросил JSON — получил техническую гарантию схемы».** Нет. Текстовая инструкция, JSON mode и поддерживаемый вывод по схеме имеют разные обещания.

**«Ключ есть в properties — значит он обязателен».** Не обязательно. Смотрим required и правила конкретного механизма.

**«Nullable означает, что ключ можно не передавать».** Нет. Допустимость null и обязательность присутствия — разные свойства.

**«Pydantic автоматически передал все мои правила серверу».** Нет. Локальные проверки и удалённая схема — разные части системы.

**«Валидный enum означает верную классификацию».** Он означает лишь попадание в допустимый набор, не соответствие тексту.

**«Любое преобразование типов полезно».** Иногда оно скрывает нарушение контракта. Для нашего извлечения явно включаем строгую проверку.

**«Схема прошла — можно выполнить действие».** Ещё нужны предметные проверки и полномочия, особенно при необратимых последствиях.

---

## 🧪 Что мы сделаем на практике

**Первый опыт — схема и локальные ответы.** Опишем модель Pydantic, посмотрим generated JSON Schema и проверим заранее заданные варианты: правильный объект, плохой JSON, пропущенное nullable-поле, строку вместо ID, лишний ключ и недопустимую категорию.

**Второй — структура против фактов.** Объект с ID 82 может пройти модель данных, но не совпасть с исходной заявкой №28. Придуманный контакт тоже может быть строкой правильного типа. Сравним это с двумя независимо заданными учебными фактами и отдельно отметим, что смысл категории ещё не проверен.

**Третий — живой запрос по желанию.** Для одного синтетического источника можно явно выбрать текстовую просьбу, JSON mode или JSON Schema, если выбранная модель и endpoint их поддерживают. Не будем угадывать доступность или автоматически повторять запрос в более слабом режиме.

По умолчанию всё работает локально без ключей и чтения `.env`. Живой запуск отделён флагом и может расходовать деньги или квоту. Никакие заявки и действия во внешних системах не создаются.

---

## ⭐ Главное из урока

1. **Свободная просьба, JSON mode и Structured Outputs — разные контракты.** Проверяем, что поддерживает конкретный сервер и модель.
2. **Схема задаёт структуру, а не истину.** Правильный тип ID и допустимая категория не доказывают соответствие источнику.
3. **Обязательное и nullable различаются.** Если данных нет, контракт должен разрешать честный исход, а не требовать выдумку.
4. **Pydantic помогает описать и проверить данные**, но локальная строгость, удалённое ограничение и бизнес-правила остаются отдельными уровнями.
5. **Принимаем результат по этапам:** завершение, синтаксис, структура, факты и полномочия. Ошибки не исправляем бесконечными скрытыми повторами.

## 📚 Глоссарий урока

- **Structured Outputs** — механизм получения результата по заданной структуре в рамках контракта API.
- **JSON mode** — режим, нацеленный на корректный JSON без обязательной гарантии нужных полей.
- **JSON Schema** — описание допустимой структуры и ограничений JSON-данных.
- **Properties** — описания полей объекта.
- **Required** — список обязательных ключей.
- **Nullable** — допустимость null как значения; не то же самое, что необязательность ключа.
- **Enum / Literal** — ограничение значения заданным набором вариантов.
- **Additional properties** — правила для неизвестных полей объекта.
- **Constrained decoding** — ограничение допустимых продолжений при генерации по определённым правилам.
- **Pydantic** — библиотека описания и валидации данных с использованием типов Python.
- **Coercion** — преобразование входного значения к другому типу при проверке.
- **ValidationError** — отчёт о нарушении правил модели данных.
- **Семантическая проверка** — проверка соответствия смыслу задачи и данным, а не только структуре.
- **Бизнес-правило** — предметное ограничение приложения, например допустимость операции и связь ID с запросом.
- **Сериализация** — преобразование объекта в формат передачи или хранения.
