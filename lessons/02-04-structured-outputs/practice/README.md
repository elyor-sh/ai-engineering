## Эксперимент 2. Девять ответов, несколько уровней проверки (15–20 минут)

```bash
uv run python $P/01_structured_outputs.py
```

Источник:

> Учебная заявка №28: не могу войти в портал. Контактный email не указан.

Правильный ID и отсутствие контакта заданы в независимой **учебной разметке**. Они не получены вторым вопросом к той же LLM и не являются универсальным механизмом извлечения фактов.

Ожидаемые наблюдения:

| Вариант | Что происходит |
|---|---|
| Нужные поля, ID 28, email null | Структура и два известных факта проходят |
| Пояснение перед JSON | Отказ синтаксического разбора |
| Нет contact_email | Структурная ошибка missing |
| ID как строка `"28"` | Строгий int отклоняет преобразование |
| Лишнее is_admin | Ошибка extra_forbidden |
| Категория вне enum | Ошибка literal_error |
| ID 82 | Структура проходит, известный факт — нет |
| Выдуманный контакт | Структура проходит, известный факт — нет |
| Допустимая метка billing | Структура и два факта проходят, но смысл категории не проверен |

Последний пример намеренный. Функция `verify_known_facts()` проверяет **только ID и контакт**. Из этого нельзя делать вывод, что она уже проверила правильность классификации, права или готовность к действию.

### Задание 2.1. Какой уровень нашёл ошибку

Для каждого случая назови уровень:

1. Завершение и тип API-результата.
2. JSON разбирается по нашим правилам.
3. Структура и типы подходят.
4. Известные факты совпадают.
5. Остальные предметные проверки и полномочия.

Почему успешный третий уровень не гарантирует четвёртый и пятый?

### Задание 2.2. Преобразование типов — решение, а не случайность

Сравни строгую модель с поведением без strict на примере `"request_id": "28"`. В каких задачах автоматическое преобразование могло бы быть удобным, а почему в нашем контракте важно увидеть исходное нарушение?

Не меняй одновременно локальный strict и API strict: это разные эксперименты.

### Задание 2.3. Неизвестное нельзя заполнять выдумкой

Почему для отсутствующего контакта предусмотрен null? Что случится, если разрешить только строку и настойчиво требовать заполнить поле?

Если в другой задаче ID вообще не указан, достаточно ли текущего контракта с обязательным int? Какой честный исход нужно спроектировать вместо угадывания?

### Задание 2.4. Откуда взялись проверяемые факты

Найди `EXPECTED_REQUEST_ID`, `EXPECTED_EMAIL` и `verify_known_facts()`.

Если заменить источник на заявку №44, какие независимые ожидания нужно пересмотреть? Почему нельзя оставлять старую разметку или брать ожидаемый ID из непроверенного результата самой модели?

### Задание 2.5. Дубликаты и безопасные ошибки

Тесты отдельно проверяют повторяющийся ключ `request_id` и нестандартный NaN. Наша приёмка отклоняет их до выбора «какое значение оставить».

Затем посмотри `safe_validation_errors()`. Почему выводит только тип нарушения и известное поле, а не полный input или текст ValidationError? Зачем неизвестный ключ заменяется безопасной подписью?

## Живой запрос — только по желанию

Основные выводы можно получить без генерации. Локальная демонстрация **не симулирует constrained decoding**: она проверяет готовые строки. Выбор `--mode` влияет на настоящий запрос только вместе с `--live`.

Один запуск делает одну попытку, не запускает чат и не исполняет действий.

### Gemini

Используются `GEMINI_API_KEY` и `MODEL_GEMINI` из окружения или корневого `.env`. Действительную модель можно указать через `--model`; автоматического устаревающего ID нет.

**Перед schema-режимом проверь поддержку JSON Schema именно этой моделью и совместимым endpoint.** Пример синтаксиса запуска:

```bash
uv run python $P/01_structured_outputs.py --live --provider gemini --mode schema
```

Два других режима задаются явно:

```bash
uv run python $P/01_structured_outputs.py --live --provider gemini --mode json
uv run python $P/01_structured_outputs.py --live --provider gemini --mode prompt
```

Не нужно выполнять все три ради галочки: каждый вызов может расходовать квоту или деньги. Сначала изучи контракт сервера. Если режим отвергнут, программа **не повторяет** запрос в другом режиме автоматически.

Что отправляется:

- `prompt`: инструкция просит JSON, специального response_format нет;
- `json`: `response_format` с `type=json_object`;
- `schema`: `response_format` с `type=json_schema`, именем, strict и локально сгенерированной схемой.

Все режимы проходят одинаковую локальную приёмку. Название режима не является поводом пропустить проверку результата.

### Ollama

```bash
open -a Ollama
ollama list
```

Если у тебя установлена действительно локальная `qwen3.5:4b`, пример для **поддерживающего схему** сервера:

```bash
uv run python $P/01_structured_outputs.py --live --provider local --model qwen3.5:4b --mode schema
```

Проверяй версию Ollama и возможности выбранного маршрута. Можно использовать `MODEL_LOCAL` вместо явного аргумента. Endpoint в этой лаборатории фиксирован как localhost, но облачный тег или алиас внутри runtime не становится локальным только из-за адреса API.

### Что ещё проверить

- Ответ полный и завершился обычным образом? `length`, refusal и инструмент не превращаются насильно в нашу структуру.
- Если schema отвергнута, какая конкретная возможность не поддерживается? Не угадывай и не начинай цикл повторов.
- Если локальная структура прошла, какие факты проверены, а какие ещё нет?
- Никакое действие с заявкой не выполняется, даже когда все локальные проверки прошли.

Лимит по умолчанию 512 выходных токенов; его можно изменить через `--max-tokens`, но это не гарантия размера видимого JSON. Скрытые повторы SDK отключены, тайм-аут ожидания — 30 секунд.

Этот пример не рассчитывает стоимость попытки. Ошибка валидации не доказывает отсутствия оплаты. Ключи не печатаются и не передаются в messages.

Тест live-ветки использует **подменённую сетевую границу**. Настоящая генерация при подготовке урока не запускалась; тесты не доказывают поддержку schema-режима твоим провайдером.

Если изменяешь контракт модели данных, проверь полученную JSON Schema и связанные тесты. Не удаляй требование только ради того, чтобы неподходящий ответ стал проходить.

## Границы реализации

Это синхронный пример извлечения из одного фиксированного источника. В нём нет email-подтверждения, универсальной проверки фактов, проверки смысла категории, авторизации, записей в систему заявок, автоматического ремонта и повторов.

`contact_email: str | None` не является полноценным валидатором адреса или его владельца. Положительный ID и совпадение двух фактов — отдельные правила кода, а не все ограничения удалённой схемы.

В настоящей системе дополнительно понадобятся соответствующие проверки содержимого, размеров, версий, прав и последствий действия. Поддержка полного JSON Schema провайдером не предполагается.
