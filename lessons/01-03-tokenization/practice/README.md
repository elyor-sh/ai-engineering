# Практика к уроку 1.3: токены, BPE и бюджет контекста

## Перед началом

Работаем из корня проекта:

```bash
cd ~/Desktop/projects/ai-engineering
uv sync
P=lessons/01-03-tokenization/practice
```

В проект добавлена библиотека `tiktoken`. В отдельном проекте её можно установить командой `uv add tiktoken`.

**Ключи Gemini и OpenRouter, Ollama и платная генерация не нужны.** При первом запуске tiktoken может скачать файлы словарей. Это загрузка данных токенизатора, а не обращение к языковой модели; затем используется кэш.

| Файл | Что делаем |
|---|---|
| `01_inspect_tokens.py` | Смотрим ID, байты и текст, сравниваем два токенизатора |
| `02_toy_bpe.py` | Учим маленький символьный BPE и применяем готовые правила |
| `03_context_budget.py` | Считаем свободное место, переполнение и условную стоимость |
| `test_experiments.py` | Проверяем обратное восстановление, BPE и арифметику |

> Важно для твоего Gemini: **tiktoken здесь не является его точным счётчиком**. У Gemini собственная токенизация. Упражнения показывают принципы, а не реальное число токенов твоего Gemini-запроса.

## Эксперимент 1. Разглядываем токены (15 минут)

```bash
uv run python $P/01_inspect_tokens.py
```

В выводе есть четыре разных вещи:

1. Длина Python-строки — количество Unicode-кодовых точек.
2. Размер текста в байтах UTF-8.
3. Количество токенов выбранного словаря.
4. Отдельные ID и байты каждого токена.

Для эмодзи `👩‍💻` у меня получилось: **3 кодовые точки, 11 байтов, 5 токенов** в `o200k_base`. Один видимый знак — далеко не обязательно один токен.

Обрати внимание на экранированные байты вроде `\xf0`: один токен может содержать лишь часть UTF-8 символа. Важно, что полная последовательность восстанавливается без потерь.

### Задание 1.1. Свои строки

```bash
uv run python $P/01_inspect_tokens.py --text "Привет"
uv run python $P/01_inspect_tokens.py --text " Привет"
uv run python $P/01_inspect_tokens.py --text "customerInvoiceProcessingService"
```

Сравни ID «Привет» с пробелом и без. Совпало ли число токенов? А сами детали? Не делай вывод только по длине списка: разбиение и ID тоже важны.

### Задание 1.2. Другой словарь

```bash
uv run python $P/01_inspect_tokens.py --encoding cl100k_base --text "Кошка спит на диване."
uv run python $P/01_inspect_tokens.py --encoding o200k_base --text "Кошка спит на диване."
```

На исходных словарях у меня получилось 12 и 9 токенов. Английская фраза `The cat is sleeping on the couch.` заняла 8 токенов в обоих.

Что показывает этот пример? **Не** универсальное соотношение языков, а зависимость конкретного текста от конкретного токенизатора.

## Эксперимент 2. Собираем BPE (10–15 минут)

```bash
uv run python $P/02_toy_bpe.py
```

Сначала программа смотрит на повторяющиеся слова, считает частые соседние пары и сохраняет правила. Затем кодирует новые слова, **не меняя** эти правила.

Маркер `</w>` — учебная отметка конца слова. Он не является настоящим служебным токеном Gemini или OpenAI. Наша игрушка начинает с букв, а не с байтов и не реализует всех деталей настоящих токенизаторов.

### Задание 2.1. Проследи одно слово

Найди, на каком шаге две детали `к` и `о` стали `ко`, а затем появилась деталь `кот`. Почему `котёнок` всё ещё приходится собирать из нескольких частей?

### Задание 2.2. Измени обучающие данные

Добавь в `words` десять повторов слова `пёс`. Посмотри, какие пары теперь объединяются раньше. Как частота текста повлияла на «удобство» словаря для этого слова?

### Задание 2.3. Остановись раньше

Замени `steps=6` на `steps=2`. Как изменилось разбиение `котик`? Восстанавливается ли исходное слово, даже если крупных деталей стало меньше?

### Задание 2.4. Найди границу аналогии

В игрушке новое слово сохраняется через буквы. В реальном байтовом варианте BPE начальные детали — байты. Почему неправильно называть эту программу полной копией токенизатора LLM?

## Эксперимент 3. Упаковываем контекст (10–15 минут)

```bash
uv run python $P/03_context_budget.py
```

Здесь **не используется токенизатор**: числа уже заданы, задача — правильно распределить бюджет условной модели с общим лимитом входа и выхода.

Исходные числа:

- общее окно — `8192`;
- инструкции и служебное оформление — `500`;
- история — `1500`;
- вопрос — `200`;
- резерв ответа — `1000`;
- дополнительный запас — `300`.

Документам остаётся **4692**. Три фрагмента занимают **4900**, то есть есть переполнение на **208**. После удаления последнего фрагмента полный вход равен **5600**.

### Задание 3.1. Сначала бумага

Проверь остаток для документов вручную. Почему нельзя отдать документам все 8192 токена? Что в этом примере уже включено в первые 500?

### Задание 3.2. Решение для RAG

Представь, что именно последний документ содержит ответ, а первые два — только общую информацию. Почему «всегда удалить последний фрагмент» — плохое правило для настоящего продукта?

Предложи два способа уложиться в бюджет, не потеряв нужный ответ. Подсказки: история, извлечение нужного фрагмента, выбор источников. Большая модель — не единственный вариант.

### Задание 3.3. Цена

В скрипте **выдуманный тариф**, а не прайс Google: доллар за миллион входных токенов и пять долларов за миллион выходных.

Проверь руками: 5600 на входе и 1000 на выходе дают **$0.0106** за запрос и **$106** за 10 000 запросов.

Затем замени `actual_output = 1000` на `actual_output = 200`, не меняя резерв `output_reserved = 1000`. Почему цена уменьшилась, хотя под ответ мы по-прежнему оставляем столько же места?

### Мои наблюдения

```text
3.1
3.2 Два способа сохранить полезные сведения:
3.3 При выходе 200 токенов цена …; резерв и расход отличаются тем, что …
```
