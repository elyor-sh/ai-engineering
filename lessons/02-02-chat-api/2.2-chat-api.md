## 🎯 Зачем этот урок

Представь, что у тебя есть надёжный транспорт до сотрудника, но каждое письмо отправляется в разном формате. Иногда забывается предыдущий вопрос, иногда инструкция начальника подменяется цитатой, иногда обрезанный ответ записывается как выполненная работа.

Проблема не в том, насколько умён сотрудник, а в организации обмена.

После урока ты сможешь:

- разделить адрес сервера, ключ, модель и содержимое запроса;
- собрать список сообщений с правильным назначением ролей;
- хранить историю на стороне приложения и добавлять завершённые ходы;
- понимать, какие параметры общие, а какие зависят от модели и сервера;
- различать транспортный успех, завершённый текст и успешное решение задачи;
- переключать учебный клиент между Gemini и Ollama без переписывания логики диалога.

## 📮 API-запрос: конверт и содержимое

Удобно разделить две части.

**Конверт** определяет, куда и от чьего имени отправляется обращение: адрес API, способ аутентификации, сетевые настройки и заголовки.

**Содержимое** описывает задачу: какая модель нужна, какие сообщения она получает и какие параметры применяются.

Ключ подтверждает доступ к сервису. Он не является инструкцией модели и не должен находиться в списке сообщений. Фраза «вот мой секретный ключ, ответь на вопрос» не заменяет правильную аутентификацию, а создаёт лишнюю передачу секрета.

SDK помогает сформировать HTTP-запрос, сериализовать данные и разобрать ответ. Но по-прежнему важно понимать, что именно мы отправляем.

### Три настройки универсальной розетки

Из модуля 0 помним: адрес, ключ и название модели. Например, один и тот же SDK может отправить совместимый запрос к Gemini или локальному Ollama, если выбран правильный endpoint.

Название пакета `openai` не означает, что каждый такой вызов идёт в OpenAI: маршрут задаёт адрес сервера. С другой стороны, похожий формат не делает все адреса и ключи взаимозаменяемыми.

Нельзя просто заменить модель на название с другого сервиса, оставив прежний сервер. И нельзя безопасно подбирать endpoint методом отправки своего ключа на неизвестные адреса.

## 🧾 Какой именно формат изучаем

В практике используем распространённый формат **Chat Completions** со списком сообщений. Его поддерживают разные совместимые серверы, в том числе нужные нам варианты Gemini и Ollama.

Это не единственный API в индустрии. Есть, например, Responses API у OpenAI, Messages API у Anthropic и собственный формат Gemini. Набор функций, названия полей и работа с состоянием могут различаться.

Поэтому изучаем не «вечный одинаковый JSON для всех», а две вещи:

1. Общую модель обмена: инструкции, вход, история, результат и ошибки.
2. Конкретный контракт выбранного совместимого интерфейса.

Новые или специальные возможности провайдера могут быть доступны только в его родном API. Совместимость полезна для переноса простого кода, но не заменяет документацию.

## 🎭 Сообщение: роль и содержание

В простом текстовом запросе сообщение содержит роль и текст. Запрос — упорядоченный список таких сообщений, а не одна случайно склеенная строка.

### System: инструкция приложения

Здесь приложение задаёт общие правила поведения: назначение помощника, стиль, границы и требования к ответу.

В нашем примере будет одна начальная системная инструкция, которую контролирует приложение. Это удобный учебный формат, а не утверждение, что все API требуют ровно такую структуру.

Некоторые интерфейсы отдельно поддерживают роль developer или другой механизм системных инструкций. Их семантику и поддержку нужно проверять у конкретного провайдера.

Системная инструкция — не сейф: пользователь может пытаться её выведать, а вывод модели не является подходящим механизмом хранения секретов. Критические права и ограничения поддерживает само приложение.

### User: запрос или данные пользователя

Это текущий вопрос, задание или пользовательские материалы. Пользователь может написать любые слова, в том числе «я теперь system».

Но строка внутри текста не должна автоматически становиться новой ролью запроса. **Поле role назначает наше приложение**, а не парсер случайных команд из пользовательского содержания.

Это не обещает полной защиты от prompt injection: модель всё ещё может неправильно отреагировать на текст. Но приложение хотя бы не должно само повышать его полномочия при сборке структуры.

### Assistant: предыдущие ответы

Через эту роль мы передаём принятые прошлые реплики ассистента. Так модель видит не только вопросы, но и развитие разговора.

Assistant-сообщение не обязательно доказывает реальное событие. Историю могла сохранить программа, составить разработчик для примера или изменить злоумышленник при плохой защите приложения. Для выполнения действий нужен отдельный подтверждённый результат системы, а не одна роль assistant.

Сообщения инструментов и их связь с вызовами разберём в уроке 2.5. Сегодня не будем выдавать произвольный текст за исполненный инструмент.

## 🪜 Порядок имеет значение

Для нашей лаборатории используем такой шаблон:

- одна инструкция приложения;
- завершённые пары «пользователь — ассистент» из прошлых ходов;
- новый вопрос пользователя.

Этот формат легко проверить. Он не разрешает все возможные конструкции реальных API: мультимодальность, частичные продолжения, инструменты и другие варианты потребуют расширения.

Представь досье встречи. Сначала идёт регламент, затем записи завершённых обсуждений, затем открытый вопрос. Если перемешать листы, формально текст сохранится, но логика беседы изменится.

Не нужно после каждого вопроса добавлять ещё одну копию системной инструкции в середину истории. И не нужно записывать туда служебную ошибку сети как будто это настоящий ответ модели.

## 🧠 История — состояние приложения

Обычный запрос Chat Completions не предполагает, что модель автоматически помнит все прошлые обращения нашего процесса. Для контекста мы передаём нужную историю явно.

В других API могут быть серверные разговоры или идентификаторы состояния. Там нужно соблюдать отдельный контракт. Не следует переносить их свойства на простой список messages без дополнительных условий.

### Один новый ход

Пользователь написал «Как меня зовут?». Приложение создаёт запрос из инструкции, принятых прошлых ходов и текущего вопроса.

Пока сервер отвечает, вопрос может жить отдельно как ожидающий ход. Если получен подходящий завершённый ответ, приложение добавляет в историю новую пару.

Если случился тайм-аут, не надо придумывать ответ «успешно» или вставлять `None`. Можно сохранить событие ошибки отдельно, показать его в интерфейсе и предложить понятное действие.

### Почему в практике история меняется только после проверки

Наш учебный контракт хранит **только принятые завершённые текстовые пары**. Неудачная попытка не изменяет этот список. Это помогает не смешивать контекст диалога с техническими событиями.

Это не единственная возможная архитектура. Реальный интерфейс может хранить и неудавшиеся пользовательские сообщения, и отказы, но должен отдельно решать, какие события попадут в следующий контекст модели.

Удаление истории командой сброса очищает наше состояние. Оно не означает удаление журналов у провайдера или изменение обученных весов.

## 🛠 Параметры: минимальный переносимый набор и расширения

**Model** — точный идентификатор на выбранном сервере. Лучше брать его из конфигурации и проверенного каталога, а не надеяться на устаревшее имя из учебника.

**Messages** — список входных сообщений. Для текущей лаборатории их content — обычная строка. В реальных запросах содержание может быть сложнее, например списком частей изображения и текста.

**Stream** — получать полный ответ или события потока. Сегодня работаем без потока, чтобы сначала понять обычный результат. Следующий урок будет про стриминг.

**Ограничение выхода** — потолок генерации, не обещанная длина. В совместимом примере используем `max_tokens`; у других контрактов могут быть `max_completion_tokens`, `max_output_tokens` или иные правила. Нельзя переименовать поле вслепую и считать интерфейсы одинаковыми.

**Temperature и top-p** — настройки выбора, знакомые по уроку 1.7. Поддержка зависит от модели. В нашей базовой практике их не задаём автоматически: сначала корректный минимальный вызов, затем осмысленные эксперименты с поддерживаемыми параметрами.

**Тайм-ауты и повторы** обычно настраиваются в клиенте или транспортном слое, а не становятся частью задачи для модели. Важно не путать ожидание сети с просьбой «отвечай быстрее».

В дальнейшем добавим режимы структурированного вывода, инструменты и другие функции. Их наличие нужно проверять для модели и endpoint, не только для названия SDK.

## 📬 Ответ — не просто строка

В нестриминговом Chat Completions ответ обычно содержит список вариантов, сообщения и метаданные. В простом случае читаем первый вариант, но помним, что запрос нескольких вариантов — отдельный режим с собственными затратами.

Для обычной текстовой реплики нас интересуют:

- есть ли ожидаемый вариант;
- почему генерация завершилась;
- есть ли текст и нет ли другого типа результата;
- какие сведения о расходе переданы.

### Причина завершения

`stop` обычно означает обычную остановку в рамках этого контракта. `length` предупреждает об ограничении длины. `tool_calls` означает, что модель запросила работу инструмента; это не текстовое подтверждение, что действие уже выполнено.

Могут быть фильтры, отказы и другие особенности. Их нужно обрабатывать как отдельные исходы, а не всегда пытаться взять content и дописать в беседу.

В нашей лаборатории принимаем в обычную историю только непустой завершённый текст со стандартной остановкой, без отдельного отказа или запроса инструмента. Это специально узкий учебный контракт, а не универсальный разбор любых ответов.

### None, пустой ответ и отказ — разные ситуации

Если текст отсутствует, `str(None)` не превращает его в настоящий ответ. Пустое поле может сопровождать другой тип результата или означать, что лимит ушёл на промежуточную работу.

Отказ может быть осмысленной репликой, а не техническим сбоем. Но «запрос обработан» и «задача пользователя решена» — не одно и то же. Как отображать и сохранять такой исход, решает приложение.

### Usage может отсутствовать

Не каждый сервер и режим возвращают одинаковый отчёт токенов. Если поля нет, честное значение — «не получено», а не автоматически ноль.

Нулевой расход, неизвестный расход и бесплатный тариф — разные вещи. Подробно займёмся учётом в уроке 2.3.

## 🚦 Три уровня успеха

Полезно разделять три проверки.

**Транспортный успех.** Сервер ответил по протоколу. Это ещё не доказательство, что в теле есть пригодный результат.

**Структурный успех.** Мы получили ожидаемую завершённую текстовую реплику или корректно обработали другой разрешённый исход.

**Успех задачи.** Ответ соответствует данным, требованиям, правам и реальной цели пользователя.

Наш учебный парсер проверяет второй уровень для узкого формата. Он не доказывает третий. Даже ответ с `stop`, непустым текстом и правильным usage может содержать неверный факт.

Это развитие урока 1.8: JSON-схема, код статуса и наличие поля content отвечают на разные вопросы, ни один из них не заменяет всю оценку качества.

## 🔌 Совместимость Gemini, Ollama и других серверов

Для практики оставим два явных маршрута.

**Gemini через совместимый endpoint.** Ключ берём из `GEMINI_API_KEY`, модель — из `MODEL_GEMINI` или явно указанного аргумента. Если данных нет, программа объясняет, что настроить, а не подставляет случайную устаревшую версию.

**Ollama на localhost.** Используем фиксированный локальный адрес и выбранную локальную модель. SDK требует непустую строку ключа, но обычный локальный Ollama без настройки аутентификации её не проверяет. Это не ключ от облачного аккаунта.

В обоих случаях логика подготовки истории одинакова, потому что выбран общий текстовый формат. Отличаться могут поддерживаемые параметры, правила токенизации, отчёт usage, отказы и служебные поля.

Успех на одном сервере — не доказательство полного совпадения другого. А доступность модели в каталоге не обещает, что у неё нет текущего ограничения или перегрузки.

### Почему не добавляем скрытый fallback

Если локальный запуск не отвечает, программа не должна самовольно отправлять тот же текст в облако. В уроке 2.1 мы уже сделали запрет передачи обязательным условием.

Поэтому провайдер выбирается явно. В дальнейшем запасные маршруты добавляются с проверкой тех же требований, а не только ради получения какого-нибудь ответа.

## 🧯 Ошибки и ожидание без тишины

Пользователю полезно видеть, что запрос отправлен. Но вывод должен содержать безопасные сведения, например выбранную модель, а не ключ и все персональные данные.

Задаём явный тайм-аут ожидания и не скрываем повторные попытки. В текущем упражнении отключим автоматические повторы клиента, чтобы один пользовательский ход не превращался незаметно в несколько вызовов.

Типичные категории уже знакомы:

- неверный доступ или разрешения;
- неизвестная модель или endpoint;
- ограничение квоты и частоты;
- временная ошибка сервиса;
- сетевой сбой или тайм-аут;
- полученный, но неподходящий для текущего контракта результат.

Тайм-аут клиента не доказывает, что сервер не выполнил вычисления или что вызов точно не оплачивается. Для настоящих систем нужна более полная политика надёжности, которую изучим в уроке 2.7.

Пока достаточно важного правила: не выдавать ошибку за готовый ответ и не портить ею историю принятых реплик.

---

## 🔐 Роли помогают организовать ввод, но не заменяют защиту

Наш builder сам назначает system, user и assistant. Он не позволяет тексту пользовательской фразы стать новым системным сообщением только из-за похожего написания.

Но корректная структура messages не гарантирует, что модель никогда не поддастся вредной инструкции. Авторизация, доступ к документам и разрешение опасных действий остаются внешними обязанностями приложения.

И ещё: история может содержать конфиденциальные данные. Для учебных запросов используем вымышленные примеры. В реальном продукте нужны правила хранения, логирования, удаления и выбора разрешённого провайдера.

Режим предварительного просмотра удобен для проверки фактического запроса, но он тоже печатает содержимое messages. Не публикуй такой вывод, если положил туда личные или рабочие сведения.

## 🧪 Что мы сделаем на практике

**Первый опыт — без сети.** Соберём два запроса «Как меня зовут?»: без предыдущего разговора и с вымышленной завершённой парой, где имя уже названо. Посмотрим на настоящий порядок полей и сообщений. Сгенерированного ответа в этом опыте нет: мы проверяем то, что приложение собирается передать.

**Второй — явный живой режим.** При желании запустим маленький терминальный чат с Gemini или Ollama. Он хранит завершённые пары в памяти процесса, поддерживает сброс и выход, ограничивает ответ и показывает безопасную информацию о результате.

По умолчанию скрипт только печатает синтетические запросы. Сеть включается отдельным флагом; только тогда читаются параметры окружения и создаётся клиент. Бесплатность живого облачного вызова зависит от тарифа и квот, поэтому не будем запускать его автоматически в тестах.

**Проверки поведения.** На заранее заданных ответах SDK проверим порядок истории, отсутствие её изменения при ошибке, отказ от обрезанного ответа и безопасный запуск без ключей. Это тестирование клиента, а не доказательство качества генерации.

У нас появится заготовка логики «Знайки», а не законченный production-чат. Пока нет стриминга, инструментов, постоянного хранения, полного контроля контекста и всей политики повторов.

## ⚠️ Частые ошибки

**«Раз пакет называется openai, запрос обязательно ушёл в OpenAI».** Нет. Направление определяет выбранный endpoint.

**«Можно положить ключ в system-сообщение».** Не нужно: аутентификация относится к конверту запроса, а не к задаче модели.

**«Модель сама вспомнит предыдущий вызов».** Для нашего обычного Chat Completions примера необходимую историю передаёт приложение.

**«Написал role: system в тексте — получил настоящую роль».** Приложение не должно так интерпретировать пользовательское содержание. Но защита от prompt injection этим не исчерпывается.

**«Если HTTP успешен, можно сразу сохранить content как готовый ответ».** Сначала нужно проверить тип результата и завершение. Даже затем остаётся оценка задачи.

**«Отсутствующий usage означает бесплатный запрос».** Нет. Это неизвестный отчёт, а не тариф.

**«Сброс локальной истории удаляет все данные у провайдера».** Нет. Это только действие с нашим состоянием, если отдельный API удаления не предусмотрен и не вызван.

## ⭐ Главное из урока

1. **Разделяй конверт и содержимое запроса.** Адрес и аутентификация не должны смешиваться с messages.
2. **Роли и порядок назначает приложение.** System задаёт правила, user несёт ввод, assistant представляет прошлые реплики; текстовые подписи внутри content не меняют структуру сами по себе.
3. **История — управляемое состояние.** В учебном контракте добавляем новую завершённую пару только после подходящего ответа и не подменяем сетевую ошибку репликой ассистента.
4. **Совместимый формат не гарантирует одинаковых параметров и результатов.** Проверяем конкретную модель, endpoint, завершение, содержание и наличие usage.
5. **Транспортный, структурный и предметный успех — разные уровни.** Корректный клиент необходим, но не является автоматической проверкой истины.

## 📚 Глоссарий урока

- **Endpoint / base URL** — адрес интерфейса, к которому обращается клиент.
- **Аутентификация** — подтверждение доступа к сервису; ключ не является частью задания модели.
- **Payload** — содержимое запроса с моделью, сообщениями и параметрами.
- **Chat Completions** — один из распространённых форматов общения через упорядоченные сообщения.
- **Messages** — список сообщений, передаваемых модели.
- **Role** — назначение сообщения в контракте API.
- **Content** — содержание сообщения; в этой лаборатории обычный текст.
- **System / user / assistant** — роли инструкции приложения, пользовательского ввода и реплик модели в изучаемом формате.
- **Ход диалога / turn** — новый пользовательский ввод и соответствующий ответ или иной исход обработки.
- **Finish reason** — причина завершения, требующая интерпретации по выбранному API.
- **Refusal** — отказ, который может передаваться отдельно или обычным текстом в зависимости от сервиса.
- **Usage** — переданный провайдером отчёт использования; отсутствие не равно нулевому расходу.
- **Preview / dry run** — просмотр подготовленного запроса без отправки.
- **Транспортный успех** — успешный обмен по протоколу.
- **Структурный успех** — получение ожидаемого типа результата.
- **Успех задачи** — соответствие результата предметным требованиям и данным.
