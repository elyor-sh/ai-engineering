## 🧭 Где мы в курсе

Это курс «AI Engineering с нуля». Его цель — научиться строить продукты на основе больших языковых моделей: от простого чат-бота до систем, которые отвечают на вопросы по документам компании, ищут информацию по смыслу с помощью векторных баз данных, и агентов, которые сами пользуются инструментами. Курс состоит из пяти частей: фундамент, поиск и знания, агенты, модели и продакшн. Сейчас мы в нулевом модуле «Старт», это его второй урок из трёх.

### Что было раньше

**Обзор курса.** Мы ввели главную метафору всего курса: языковая модель — это гениальный новый сотрудник. Он прочитал почти весь интернет, но у него три слабости: он не знает данных вашей компании, иногда уверенно выдумывает и не имеет рук — может только говорить. Весь курс посвящён тому, как эти слабости закрыть.

**Урок 0.1 «Что такое AI Engineering».** AI-инженер строит продукты поверх готовых моделей-основ, а не обучает модели с нуля. Модели-основы похожи на электросеть: компании больше не строят свой генератор, а подключаются к «розетке интеллекта» через API. У AI-инженера четыре рычага: инструкция, то есть промпт; справочник, то есть RAG; доступ к системам — инструменты и агенты; и обучение — fine-tuning. Применяем их от простого к сложному. Главная мысль урока: модель — это двигатель, но не автомобиль: вызов модели — лишь один шаг из девяти в типичном приложении, а всё остальное — обычная инженерия. И ещё: LLM-системы недетерминированы, ошибаются тихо, а каждый вызов стоит денег и времени.

### Как с этим связан этот урок

В прошлом уроке мы выяснили, что AI-инженер — это прежде всего разработчик, и что большая часть его работы — инженерия вокруг модели. Чтобы строить этот «автомобиль вокруг двигателя», нужна мастерская. В этом уроке мы её собираем. А также подключаемся к той самой «розетке интеллекта»: получаем ключи от облачных провайдеров и ставим собственную «мини-электростанцию» — локальную модель на своём компьютере.

## 🐍 Почему Python

AI-инженером можно работать на разных языках: TypeScript, Go, Java, C#. Но Python здесь — бесспорный лидер, и на это есть причины.

Во-первых, весь мир машинного обучения исторически вырос на Python. Библиотеки для работы с нейросетями, данными, эмбеддингами, векторными базами появляются в первую очередь на нём, а на других языках — позже или никогда.

Во-вторых, все крупные провайдеры моделей выпускают официальные библиотеки для Python, и обычно они самые полные и актуальные.

В-третьих, Python удобен для экспериментов. Работа AI-инженера во многом исследовательская: попробовал промпт, посмотрел на ответ, поменял, сравнил. Python и интерактивные блокноты идеально подходят для такого ритма.

Поэтому основной язык курса — Python. Если ты пишешь на другом языке — не страшно: синтаксис Python простой, а все идеи курса переносятся на любой язык.

## 📦 Виртуальные окружения: отдельная кухня для каждого блюда

Представь, что ты готовишь сразу несколько блюд на одной кухне. Для одного нужна соль одной марки, для другого — другой, а третье блюдо требует старую версию рецепта. Если всё лежит на одной полке, рано или поздно что-то перепутается.

С программами то же самое. Один проект требует библиотеку версии 1, другой — версии 2. Если устанавливать всё «глобально», в систему, проекты начинают мешать друг другу. Это называют «адом зависимостей».

Решение — **виртуальное окружение**. Это изолированная папка внутри проекта, в которой лежит своя копия Python и свои библиотеки нужных версий. Проекты больше не мешают друг другу. А если окружение сломалось, его можно просто удалить и пересоздать за секунды.

Отдельное правило для Mac: в системе уже есть Python, которым пользуется сама macOS. Его лучше никогда не трогать и ничего в него не устанавливать. Мы будем работать только внутри виртуального окружения проекта.

## ⚡ Менеджер пакетов uv

Раньше в Python для управления окружениями и библиотеками нужно было несколько разных инструментов: один для установки версий Python, другой для создания окружений, третий для установки пакетов. Новичков это сильно путало.

**uv** — современный инструмент, который делает всё это сразу. Он устанавливает нужную версию Python, создаёт виртуальное окружение, ставит библиотеки и запускает программы. И делает это очень быстро — установка, которая раньше занимала минуту, с uv занимает секунды. За последние пару лет uv стал фактическим стандартом в новых Python-проектах.

С uv в проекте появляются два важных файла.

**pyproject.toml** — это как список покупок: «нужна библиотека openai, нужна библиотека anthropic». Здесь описано, что проекту нужно, без жёсткой привязки к конкретным версиям.

**uv.lock** — это как кассовый чек: «куплено openai версии такой-то, anthropic версии такой-то, плюс ещё сорок вспомогательных библиотек точно таких-то версий». Lock-файл фиксирует точное состояние. Благодаря ему проект через полгода или на другом компьютере соберётся ровно так же.

Главная команда, которую ты будешь использовать постоянно, — запуск программы через uv. uv сам проверит, что окружение в порядке и все библиотеки на месте, и только потом запустит код. Вручную «активировать» окружение не обязательно.

## 📓 Jupyter: лабораторный журнал

Обычная программа запускается целиком: от первой строки до последней. Для экспериментов это неудобно. Представь, что ты загрузил тысячу документов, посчитал для них эмбеддинги — это заняло пять минут, — и теперь хочешь попробовать десять разных вариантов поиска. Перезапускать всё с нуля каждый раз — мучение.

**Jupyter-блокнот** решает эту проблему. Код разбит на ячейки, и каждую можно запускать отдельно. Результат выполнения остаётся в памяти: загрузил данные один раз — и дальше экспериментируй сколько угодно. А под каждой ячейкой сохраняется её вывод: текст, таблицы, графики. Получается живой лабораторный журнал.

Но у блокнотов есть и опасная сторона. Ячейки можно запускать в любом порядке, и легко оказаться в ситуации, когда блокнот работает только потому, что ты когда-то запустил ячейку, которую потом удалил. Поэтому правило простое: блокнот — для экспериментов и исследований, а код, который должен работать надёжно, переносится в обычные Python-файлы.

Кстати, многие редакторы, включая Zed и VS Code, умеют запускать ячейки прямо в обычном Python-файле, если разделить код специальными комментариями. Это удобный компромисс между блокнотом и обычным кодом.

## 🔑 API-ключи: пропуск и кредитная карта в одном

Чтобы обратиться к облачной модели — например, от OpenAI, Anthropic или Google, — нужен **API-ключ**. Это длинная секретная строка, которую ты получаешь в личном кабинете провайдера и прикладываешь к каждому запросу.

API-ключ — это одновременно пропуск и кредитная карта. По нему провайдер понимает, кто ты, и списывает деньги за каждый запрос. Оплата обычно идёт за токены — маленькие кусочки текста, о которых мы подробно поговорим в первом модуле. Чаще всего сначала нужно пополнить баланс, а потом он расходуется по мере запросов.

Отсюда главное правило безопасности: **ключ — это деньги**. Если он утечёт, кто-то другой будет пользоваться моделями за твой счёт. И это не теоретическая угроза. Существуют боты, которые постоянно сканируют публичные репозитории в поиске случайно опубликованных ключей. Ключ, попавший на GitHub, могут найти и начать использовать в течение нескольких минут.

Как защищаться:

**Никогда не пиши ключ прямо в коде.** Ключи хранятся в отдельном файле с названием «.env» — сокращение от environment, окружение. Программа при запуске читает этот файл и получает ключи как переменные окружения.

**Файл .env никогда не попадает в git.** Для этого его имя добавляют в специальный файл .gitignore — список того, что система контроля версий должна игнорировать. А чтобы другие люди знали, какие ключи нужны проекту, рядом кладут файл-шаблон «.env.example» — с названиями переменных, но без самих значений.

**Ставь лимиты расходов.** У большинства провайдеров в личном кабинете можно задать максимальный бюджет. Даже если что-то пойдёт не так — например, программа уйдёт в бесконечный цикл запросов, — ты не потеряешь больше заданной суммы.

**Если ключ утёк — сразу отзови его** в личном кабинете и создай новый. Удалить коммит из истории недостаточно: ключ уже могли скопировать.

И ещё одно важное замечание о приватности. Бесплатные тарифы некоторых провайдеров могут использовать твои запросы для улучшения своих моделей. Поэтому через бесплатные тарифы не стоит отправлять конфиденциальные данные: рабочие документы, персональные данные клиентов, секреты компании.

## 🌐 Провайдеры моделей и «универсальная розетка»

Моделей сегодня очень много, и их предоставляют разные компании. Основные варианты для нашего курса:

**OpenAI** — создатели GPT и ChatGPT. Их формат API стал отраслевым стандартом.

**Anthropic** — создатели моделей Claude. Сильны в работе с длинными документами, в программировании и в агентных задачах.

**Google** — модели Gemini. Удобны тем, что у Google AI Studio есть бесплатный тариф с ограничениями, на котором можно учиться.

**OpenRouter** — это не создатель моделей, а агрегатор. Один ключ и один баланс дают доступ к сотням моделей разных компаний: и закрытых, и открытых. Для обучения это очень удобно: можно сравнивать модели, не регистрируясь у каждого провайдера. Среди них есть и бесплатные варианты с ограничениями на число запросов.

**Локальные модели** — модели, которые работают прямо на твоём компьютере. О них — в следующем разделе.

Теперь важная идея. Когда OpenAI выпустила свой API, многие разработчики начали писать под него код. И остальные компании поступили разумно: сделали свои API совместимыми с форматом OpenAI. Сегодня так называемый **OpenAI-совместимый API** поддерживают OpenRouter, Google, локальный Ollama и множество других сервисов.

Это как универсальная розетка. Один и тот же код может работать с совершенно разными моделями — нужно поменять только адрес сервера и название модели. Сегодня ты отправляешь запрос в облако, завтра — локальной модели на своём ноутбуке, а сам код почти не меняется. В курсе мы будем активно этим пользоваться.

При этом у некоторых провайдеров, например у Anthropic, есть и собственный формат API со своими дополнительными возможностями. С ним мы тоже познакомимся.

## 💻 Локальные модели и Ollama

Не все модели живут в облаке. Многие компании публикуют свои модели открыто: их можно скачать и запустить на собственном компьютере. Это открытые модели — например, семейства Qwen, Llama, Gemma, Mistral, DeepSeek.

**Зачем запускать модели локально?**

- **Бесплатно.** Платишь только за электричество.
- **Приватно.** Данные никуда не уходят с твоего компьютера. Для работы с конфиденциальными документами это может быть решающим аргументом.
- **Без интернета.** Работает даже в самолёте.
- **Для экспериментов.** Можно делать тысячи запросов, не думая о счёте.

**Минусы тоже есть.** Локальные модели обычно слабее лучших облачных, особенно в сложных рассуждениях. Они работают медленнее. И они требуют много памяти.

**Ollama** — самый простой способ запускать открытые модели локально. Это программа, которая скачивает модели одной командой, запускает их и поднимает на твоём компьютере локальный сервер с OpenAI-совместимым API. То есть код, который ты напишешь для облачной модели, сможет работать и с локальной — та самая универсальная розетка.

### Сколько памяти нужно модели

Размер модели измеряется в **параметрах** — это числа внутри нейросети, её «знания». Пишут их с буквой B — billion, миллиард. Модель на 4B — это четыре миллиарда параметров, на 9B — девять миллиардов, на 70B — семьдесят.

Каждый параметр нужно где-то хранить. В полном виде параметр занимает два байта, поэтому модель на 9 миллиардов параметров заняла бы около восемнадцати гигабайт. Это много. Поэтому для локального запуска модели сжимают — эта техника называется **квантизацией**. Её можно сравнить со сжатием музыки в MP3: файл становится в несколько раз меньше, а качество падает незначительно. В самом популярном варианте, 4-битном, на каждый миллиард параметров приходится примерно от половины до одного гигабайта. Так модель на 9 миллиардов параметров превращается из восемнадцати гигабайт примерно в шесть–восемь.

Простое практическое правило: модели нужно чуть больше памяти, чем весит её файл, — плюс запас на обработку текста. И ещё сама система и твои программы тоже хотят память.

### Почему Mac хорош для локальных моделей

У компьютеров Mac на чипах Apple Silicon — M1, M2, M3, M4 — есть особенность: **единая память**. Обычно у компьютера есть оперативная память для процессора и отдельная, гораздо меньшая, память видеокарты. А нейросети быстрее всего работают именно на видеокарте. На Mac же процессор и графическое ядро используют одну общую память. Поэтому Mac с 24 гигабайтами памяти может отдать большую её часть под модель — для обычного ПК это потребовало бы дорогой видеокарты.

Ориентиры для Mac с 24 гигабайтами памяти:

- модели на 3–4 миллиарда параметров работают очень быстро и подходят для простых задач и экспериментов;
- модели на 8–14 миллиардов — хороший баланс качества и скорости, основной рабочий вариант;
- модели на 25–30 миллиардов запустятся, но впритык по памяти и заметно медленнее;
- модели на 70 миллиардов и больше — уже не для этого компьютера.

## 🗂 Как устроен наш проект

Весь курс живёт в одной папке — одном репозитории. В ней лежат план курса, тексты для NotebookLM, папки уроков с теорией и практикой и сквозной проект «Знайка». На всю папку — одно общее виртуальное окружение, которое создаёт uv. Так установленные библиотеки доступны в любом уроке, и не нужно настраивать окружение заново.

В корне проекта будут лежать:

- **pyproject.toml и uv.lock** — список библиотек и их точные версии;
- **.python-version** — какую версию Python использовать;
- **.venv** — само виртуальное окружение, в git не попадает;
- **.env** — твои секретные ключи, в git не попадает;
- **.env.example** — шаблон с названиями ключей, в git попадает;
- **.gitignore** — список того, что git игнорирует.

## ⭐ Главное из урока

1. **Python** — основной язык AI-инженерии: все библиотеки и SDK появляются в первую очередь на нём.
2. **Виртуальное окружение** изолирует библиотеки проекта. Системный Python на Mac не трогаем.
3. **uv** управляет версиями Python, окружениями и пакетами. pyproject.toml — список покупок, uv.lock — точный чек.
4. **API-ключ — это деньги.** Храним в .env, .env — в .gitignore, ставим лимиты расходов, утёкший ключ сразу отзываем.
5. **OpenAI-совместимый API** — универсальная розетка: один код работает с облачными и локальными моделями, меняются только адрес и название модели.
6. **Локальные модели через Ollama** — бесплатно и приватно, но слабее и требуют памяти. На Mac с 24 ГБ комфортно работают модели до 14 миллиардов параметров.

## 📚 Глоссарий урока

- **Виртуальное окружение (venv)** — изолированная папка с отдельным Python и библиотеками конкретного проекта.
- **Пакет / библиотека** — готовый код, который можно установить и использовать в своей программе.
- **Зависимости** — библиотеки, которые нужны проекту для работы.
- **uv** — быстрый менеджер Python-проектов: версии Python, окружения, пакеты.
- **pyproject.toml** — файл с описанием проекта и списком его зависимостей.
- **Lock-файл (uv.lock)** — файл с точными версиями всех установленных пакетов для воспроизводимости.
- **Jupyter Notebook** — интерактивный блокнот, где код выполняется по ячейкам, а результаты сохраняются под ними.
- **Ядро (kernel)** — процесс, который выполняет код из блокнота и хранит его состояние.
- **API-ключ** — секретная строка для доступа к API провайдера; по ней идёт идентификация и оплата.
- **Переменная окружения** — именованное значение, которое программа получает от операционной системы при запуске.
- **.env** — файл с переменными окружения проекта, обычно с секретами.
- **.gitignore** — список файлов и папок, которые git не должен отслеживать.
- **Провайдер** — компания, предоставляющая доступ к моделям через API.
- **OpenRouter** — агрегатор, дающий доступ к сотням моделей через один ключ и один API.
- **OpenAI-совместимый API** — API в формате OpenAI, который поддерживают многие провайдеры и локальные серверы.
- **Открытая модель** — модель, веса которой опубликованы и которую можно запустить у себя.
- **Ollama** — программа для скачивания и локального запуска открытых моделей.
- **Параметры модели** — числа внутри нейросети; их количество (4B, 9B, 70B) определяет размер модели.
- **Квантизация** — сжатие модели за счёт уменьшения точности хранения параметров.
- **Единая память (unified memory)** — архитектура Apple Silicon, где процессор и графическое ядро используют общую память.
