## Эксперимент 1. За какие предсказания выставляют штраф (15 минут)

```bash
uv run python $P/01_training_targets.py
```

В условном диалоге пять токенов:

```text
<user>  2+2?  <assistant>  4  <end>
```

Это учебный словарь, не настоящий chat template провайдера. Текст `2+2?` мы специально считаем одним токеном в игрушке: из этого нельзя делать вывод о реальной токенизации.

Каждая входная позиция предсказывает **следующую**, поэтому получаются четыре цели. Маска SFT в этом примере включает только ответ `4` и его завершение `<end>`.

### Что получится на исходных данных

- Loss по всем четырём целям: примерно **1.4067**.
- Loss только по ответу и завершению: примерно **0.1643**.
- Если исправить только предсказания до ответа, выбранный SFT-loss останется **0.1643**.

Предсказания не стали лучше от смены способа усреднения. Мы просто изменили оцениваемое множество. Сравнивать такие два числа как «до и после улучшения модели» нельзя.

### Задание 1.1. Не ошибись на единицу

Найди `shift_targets()`. Почему маска берётся как `mask[1:]`, а не `mask[:-1]`?

Какая входная позиция предсказывает токен `4`? Входит ли в loss сама входная метка `<assistant>`, или штраф относится к следующему после неё токену?

### Задание 1.2. Сломай ответ, а не вопрос

В `target_probabilities` замени вероятность правильного токена ответа с `0.8` на `0.1`. До запуска предскажи: увеличится или уменьшится loss по ответу?

Затем верни значение и поменяй вероятность цели `2+2?` с `0.05` на `0.8`. Изменился ли SFT-loss? Почему изменилась оценка всех позиций?

### Задание 1.3. Маска потери — не маска внимания

Программа исключила пользовательские цели из выбранного loss. Значит ли это, что настоящей модели нельзя видеть вопрос?

Может ли градиент от ответа затронуть общие параметры, участвовавшие в обработке входа? Почему нельзя из примера сделать вывод, что «веса вопроса заморожены»?

## Эксперимент 2. Меньше loss — но хуже выбор (20 минут)

```bash
uv run python $P/02_preferences_and_reward.py
open $P/out/02_preferences_and_reward.png
```

В искусственном регламенте опыта указан срок **14 дней**. Второй готовый ответ уверенно заявляет **140 дней**. Это не инструкция о реальных правах покупателей: все правила заданы для лаборатории.

Политика выбирает только между этими двумя ответами. Один параметр `theta` управляет вероятностями, а опорная политика остаётся фиксированной. В начале шансы равны — по 50%.

Сравниваем два набора предпочтений:

1. Правильный ответ отмечен как chosen.
2. Ошибочный длинный ответ отмечен как chosen: его предпочла нарочно плохая эвристика «больше слов — лучше».

### Что видно на графике

На исходных настройках:

- при правильном предпочтении вероятность верного ответа растёт с **0.500 до 0.981**;
- при ошибочном предпочтении падает с **0.500 до 0.019**;
- парная потеря в обоих случаях уменьшается с **0.693 до 0.132**.

На правой панели две кривые почти полностью совпадают — это ожидаемо, а не пропавший график. Для нашей симметричной игрушки успех оптимизации одинаков, хотя результат по известному учебному правилу противоположный.

Вероятность здесь — вероятность **выбора одного из двух заданных ответов**. Не переносим это число как оценку уверенности в факте на настоящие LLM.

### Задание 2.1. Что на самом деле знает алгоритм

Открой `train_toy_policy()`. Есть ли в аргументах правильный срок возврата, источник регламента или проверка фактической корректности?

Почему алгоритм выполняет свою задачу даже в плохом сценарии? Где должна была появиться проверка качества предпочтений?

### Задание 2.2. Относительно чего сравниваем

Посмотри на `dpo_pair_loss()`. Она использует не только текущие вероятности, но и `reference`. Опорная модель пересчитывается с новыми весами на каждом шаге или зафиксирована до цикла?

Не нужно выводить формулу. Главное — отличить изменение предпочтения относительно опоры от одной оценки «этот ответ сейчас вероятнее».

### Задание 2.3. Больше шагов не лечит плохую цель

В вызове `train_toy_policy()` внутри `main()` добавь `steps=200`. Что произошло с двумя сценариями?

Если неверный ответ становится ещё вероятнее, поможет ли просто «дать обучению больше времени»? Какие данные или критерии нужно исправить вместо этого?

### Задание 2.4. Не перепутай ручки

Здесь `lr` задаёт размер обновления, а `beta` — масштаб аргумента парной DPO-цели. Это не температура генерации из урока 0.3 и не универсальная настройка длины рассуждений.

Поменяй `lr` при фиксированном числе шагов и посмотри на скорость изменения вероятности. Не делай вывод «больший beta всегда лучше»: поведение зависит от цели, данных и настроек, а настоящая языковая модель гораздо сложнее.

### Что именно этот опыт НЕ доказывает

- Эвристика длины не является обученной reward model.
- Мы не воспроизводим полный RLHF, PPO или обучение reasoning-модели.
- Результат на двух ответах не доказывает свойства любой настоящей LLM.
- Мы показываем уязвимость обучающего сигнала: успешная оптимизация может усиливать неправильные предпочтения.

## Автоматические проверки

```bash
uv run python -m unittest discover -s "$P" -v
```

На исходном коде ожидается **14 тестов, OK**. Проверяются:

- согласованный сдвиг целей и маски;
- исключение выбранных позиций из усредняемой потери;
- рост штрафа при ухудшении предсказания нужного токена;
- нормировка двухответной политики и устойчивость на больших числах;
- сравнение относительно фиксированной опоры;
- один шаг аналитического градиента;
- снижение loss при правильном и при ошибочном предпочтении.

Как и раньше, тесты проверяют учебные вычисления. Они не заменяют оценку обученной модели на независимых задачах.
